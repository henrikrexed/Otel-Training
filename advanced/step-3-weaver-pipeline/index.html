    Step 3 — Weaver pipeline

    The labs/advanced/ directories keep their original feature-ordinal numbering, so they run one behind these doc steps — this page's assets live under labs/advanced/step2-weaver-semconv/.

    Optional / stretch step

    Weaver is a build-time governance guard, not a telemetry fix. If you are tight on time, skim the concept and move to Step 4 — the money-path is already observable after Steps 1–2. Come back here when you want to stop those attributes from rotting.

    Goal: stop the attributes you created in Step 1 (and reused for the Step 2 metrics) from silently rotting. You will turn the casino.* conventions into a versioned registry and a CI check that fails the pull request on drift. Budget 25 minutes.

    The concept

    Step 1 introduced casino.* attributes by hand. Without a guard, the next refactor renames casino.bet.amount → casino.betAmount, or adds a round.id dimension to a metric, and every dashboard, DQL query, and alert that depends on the old name breaks — silently. Weaver makes the conventions a versioned registry and a CI check.

    flowchart LR pr["Pull request
    renames casino.bet.amount"] --> ci["CI: weaver registry check"] ci -->|conventions intact| green["exit 0 — merge allowed"] ci -->|drift detected| red["exit non-zero — merge blocked"] red -.->|protects| dt["Dynatrace content
    stays valid"]

    The assets

    From labs/advanced/step2-weaver-semconv/:

    registry/
  registry_manifest.yaml     # registry name + version
  models/casino.yaml         # the casino.* attribute registry + span & metric conventions
weaver-policies/
  casino_policies.rego       # extra guards: snake_case naming + no high-card metric dims
ci/weaver-check.yml          # GitHub Actions workflow running `weaver registry check`

    Before — no guard

    No registry, no CI check. A rename or a stray high-cardinality dimension merges freely and Dynatrace content silently rots. This is the status quo you start from.

    ② Opencode — add the guard

    Unlike the collector steps, the fix here is a registry, not a pipeline change. Drive opencode with the otel-semantic-conventions skill to author (or extend) the registry from the casino.* attributes already in the code — goal, target dir, skill:

    opencode run "Using the otel-semantic-conventions skill: review the casino.* \
attributes and metrics used in the slots service, and make \
labs/advanced/step2-weaver-semconv/registry a complete Weaver registry covering \
casino.game.name, casino.bet.amount, casino.outcome, casino.payout.amount and \
the Step 2 metrics casino.bets.count / casino.wager.amount. Enforce snake/dotted \
naming and forbid high-cardinality metric dimensions in the rego policy."

    Review the diff, then run the same command CI runs (exit 0 means conventions intact):

    weaver registry check \
  --registry labs/advanced/step2-weaver-semconv/registry \
  --policy   labs/advanced/step2-weaver-semconv/weaver-policies

    If the agent gets it wrong — steer it back

    If the agent invents attributes the code does not emit, reply "only include casino. keys that actually appear in the slots service source and the Step 2 metrics — quote each one."* The committed registry/models/casino.yaml is the reference answer.

    Watch the guard fire

    Introduce drift and confirm it is blocked:

    # camelCase drift → policy deny
sed -i 's/casino.bet.amount/casino.betAmount/' registry/models/casino.yaml
weaver registry check --registry registry --policy weaver-policies
#  → FAIL: casino attribute 'casino.betAmount' must be snake_case (no camelCase)

    A high-cardinality dimension on the payout metric (adding - ref: casino.round.id under metric.casino.payout) is denied the same way. Revert the edit and the check goes green again.

    The CI job gates merges

    In the casino repo the weaver-semconv-check job runs on services/** changes, so drift can never reach main. Weaver is pinned in ci/weaver-check.yml.

    Dynatrace validation checkpoint

    Weaver is a build-time guard, so its primary checkpoint is CI: green vs red. The downstream Dynatrace evidence: because the names are stable, the Step 1 DQL keeps returning rows across releases.

    fetch spans
| filter span.name == "casino.slots.spin"
| summarize spins = count() by { casino.outcome }
    • With the guard: rows keep coming after every release — the attribute names never silently change.
    • Contrast (a "renamed attribute" branch with no guard): the same DQL returns zero rows — exactly the regression Weaver would have blocked.

    Definition of done

    • weaver registry check exits 0 on the intact registry
    • A camelCase rename is denied by policy
    • A high-cardinality metric dimension is denied by policy
    • The weaver-semconv-check CI job is wired for services/**
    • The Step 1 DQL still returns rows (names held stable)
